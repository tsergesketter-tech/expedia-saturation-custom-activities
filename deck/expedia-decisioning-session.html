Whiteboarding and discovery

The model events its answer out to a data extension

The recommended pathway. Journeys never call the model. They read the latest score as contact data.

  1. Decision engineScores a traveler whenever their behavior changes, or on a schedule
  2. Event outREST upsert for each change, or a bulk file to S3 that an import loads
  3. Data extensionExpedia_Saturation_Predictions, one row per traveler, exposed as contact data
  4. Journey decision splitReads the row: send, hold, or a default when there's no score

Tradeoffs

No load on the model at send time, and it scales with the audience

Only as fresh as the model's last event, with no journey context

The freshest answer, decided on the spot

Every traveler waits on a decision. When thousands enter at once they queue behind the model, so it doesn't scale well.

Fire and forget. The journey keeps moving and the model works at its own pace.

Needs a short wait step, and a default for travelers whose answer hasn't landed

Scale discussion

How each pattern holds up at scale

Recommended

C Eventing to a data extension scales

The model writes scores on its own schedule. When the journey runs, the answer is already in contact data, so nothing waits on the model.

Optional, for journey context

B Sync makes every traveler wait

Each traveler holds a connection until the model answers. When thousands enter at once, they queue at the split, and one slow response slows the whole journey.

Optional, for journey context

BC Async keeps the journey moving

The callout is fire and forget. The model answers at its own pace, and the split reads contact data when the traveler gets there.

Levers we can pull

  • Event scores to a data extension wherever a recent answer is good enough
  • Keep sync and async for the few journeys that need context
  • Raise Journey Builder throughput, such as more slot workers, where volume needs it
  • Give every decision a default path for when the model can't answer

Where we'd start: the model events scores out to a data extension that every journey reads. Sync and async calls stay optional, for journeys that need a decision made in context.

Optional: deciding in journey context

For journeys where the decision depends on the moment. Both run in our sandbox today. Marketing Cloud signs every call with a JWT so the model can verify it came from the journey.

Real-time split

One call. The answer chooses the branch.

  1. Journey to model
    Traveler reaches the split 
    POST /ca/sync/execute
{ "contactKey": "EXP-100234" }
  2. Model to journey
    Answer inside the timeout (we set 10 s, the target is well under 100 ms) 
    { "branchResult": "abstain",
  "saturationScore": 0.785,
  "reasonCodes": "HIGH_SEND_VOLUME_7D|DECLINING_OPEN_RATE" }
  3. Journey
    Routes to the Abstain branch. The answer is also saved to contact data for reporting.

Async callout

The journey never waits on the model.

  1. Journey to model
    Request, then an immediate acknowledgement 
    POST /ca/async/execute   →  { "status": "accepted" }   5 ms
  2. Journey
    Traveler moves into a wait step
  3. Model to contact data
    Scores in the background, then upserts the row 
    POST /hub/v1/dataevents/key:Expedia_Saturation_Predictions/rowset
[{ "keys": { "SubscriberKey": "EXP-100234" },
   "values": { "Prediction": "abstain", "RecommendedHoldHours": 52 } }]
  4. Journey
    Decision split reads contact data when the wait ends
